# HID 协议逆向记录

本文记录如何找到雷柏鼠标的电量数据，以及如何验证其正确性。
  
**所有结论均为本机实测所得，非推测。**

- 设备：雷柏 **VT7 MAX MASTER V2**
- 连接：2.4G 无线（USB 延长线 + 接收器）
- 主机 ID：`VID_24AE` / `PID_0x1470` — "Rapoo Gaming Device"

---

## 一、最终可用的读取方式

```
打开厂商集合   usagePage = 0xFF00, usage = 0x000F   (col06)
读取 Feature report ID = 8，缓冲 250 字节
电量百分比 = 返回数据 byte[88]      (取值 0..100)
```

**全程不向设备写入任何数据。** 句柄在启动时打开一次并保持复用，
  
避免反复 `CreateFile` / `CloseHandle` 扰动 2.4G 链路。

### 实测验证记录

官方网页驱动显示值 vs `byte[88]`：

| 官方显示              | `byte[88]`  | 结果 |
| ----------------- | ----------- | -- |
| 87%               | `0x57` = 87 | ✓  |
| 充电中 94%（读取瞬间 92%） | `0x5C` = 92 | ✓  |
| 93%               | `0x5D` = 93 | ✓  |
| 92%               | `0x5C` = 92 | ✓  |

成品连续读取稳定性：10/10、8/8、5/5 全部成功，数值一致。

### 为什么必须超额申请缓冲

`FeatureReportByteLength` 只是**声明长度**（此设备为 33 字节），
  
但设备实际会返回更多数据 —— 电量在 `byte[88]`，远超声明长度。

若按声明长度分配缓冲，`byte[88]` 永远读不到。
  
因此必须申请 **250 字节**。

## 二、设备能力矩阵（实测）

复合设备，走 Windows 通用 `usbccgp` + `HidUsb`，**未安装厂商驱动**。

| 集合                | UsagePage/Usage   | 含义       | In | Out | Feat | 用户态可访问性         |
| ----------------- | ----------------- | -------- | -- | --- | ---- | --------------- |
| `mi_00`           | `0001`/`0002`     | 鼠标       | 8  | 0   | 0    | ❌ ACCESS_DENIED |
| `mi_01&col01`     | `0001`/`0006`     | 键盘       | 9  | 2   | 0    | ❌ ACCESS_DENIED |
| `mi_01&col02`     | `0001`/`0006`     | 键盘       | 19 | 0   | 0    | ❌ ACCESS_DENIED |
| `mi_01&col03`     | `000C`/`0001`     | 消费者控制    | 3  | 0   | 0    | ⚠️ 可打开，无数据      |
| `mi_01&col04`     | `0001`/`0080`     | 系统控制     | 2  | 0   | 0    | ⚠️ 可打开，无数据      |
| `mi_01&col05`     | `FF00`/`000E`     | 厂商邮箱     | 33 | 33  | 249  | ⚠️ 可写，但**不要写**  |
| **`mi_01&col06`** | **`FF00`/`000F`** | **厂商信息** | 0  | 0   | 33   | ✅ **只读，数据来源**   |
| `mi_01&col07`     | `FF00`/`0002`     | 厂商状态     | 19 | 19  | 0    | ⚠️ 输入可读，输出被拒    |

**关键结论**：电量在 **col06 的 Feature report 8**，只需读取，无需任何写入。

> 注意 `mi_00`（真正的鼠标集合）**无权限打开** —— 这是 Windows 对
>   
> 独占输入设备的保护。所幸电量不在那里。

## 三、排除干扰字节

同一次读取里还有其他「看起来像电量」的字节，均已证伪：

| 字节             | 观测值                     | 判定       |
| -------------- | ----------------------- | -------- |
| `byte[75]`     | 94 → 94 → 94（恒定）        | ❌ 配置区恒定值 |
| `byte[98]`     | 每次读取都在跳（B4/B0/B2）       | ❌ 遥测计数器  |
| `byte[113]`    | B8 ↔ 86 反复              | ❌ 遥测     |
| **`byte[88]`** | 87 → 92 → 93 → 92（跟随电量） | ✅ **电量** |

**判别方法**：静置轮询，观察哪些字节恒定、哪些随机跳变、
  
哪些缓慢跟随真实电量变化（电量变化很慢，几十分钟才掉 1%）。

### 数据块结构（偏移 72 起，2026-10-03 修正）

```
[72] 00 00 00 00 00 00 00 00 00 | 40 02 | E8 03 | 4C 04 | 01 | 53 | 00 | 03 01 01 70 ...
                                  ↑       ↑        ↑        ↑    ↑
                                0x0240  0x03E8   0x044C    1   0x53 = 83
                                 = 576   = 1000   = 1100       电量
                                 16 位小端 DPI 档位表（严格递增）
```

`E8 03` = 1000、`4C 04` = 1100 是 **16 位小端 DPI 档位值**。

**这条结构可利用**：电量字节紧跟在这张表之后，表尾有一个恒为 `01` 的标记字节。
于是「找电量」可以退化成「找 DPI 表」：

```
严格递增的 16 位小端序列（值域约 100..30000）
  → 表尾紧随一个恒为 01 的字节
  → 再下一个字节就是电量
```

本机实测（电量 83% = 0x53）：

```
[80] 00
[81] 40 02   = 576  dpi
[83] E8 03   = 1000 dpi
[85] 4C 04   = 1100 dpi
[87] 01      ← 标记
[88] 53      = 83   ← 电量
[89] 00 03 01 01 70 46 10 00 04 B7 ...   ← 遥测区
```

三个约束缺一不可，均为实测踩出来的：

1. **必须要求严格递增** —— 否则紧邻的定长字段会被并进表里。
   例如 `byte[89..90]` 的 `01 70` 会被读成 `0x7001 = 28673`，
   把表错误延长到 `byte[91]`、电量误定位到 `byte[92]`。
2. **表尾必须是 `01`** —— 否则采样期内恰好恒定的遥测区会被当成长表。
3. **`01` 之后才是电量** —— 01 本身也落在合理值域内，容易被误选。

人工排查时按这三条筛，可把候选从十几个缩到一两个。

## 四、握手帧是个错误（重要更正）

早期实现认为需要先向 `col05` 的 output report 6 发送一帧：

```
A5 A3 00 00 00 00 00 00
```

**这个判断是错的，而且有害。**

### 实测证据

| 假设            | 实测结果                        |
| ------------- | --------------------------- |
| 「必须先握手才能读到电量」 | ❌ 完全不写设备也能稳定读到（5/5 成功）      |
| 「定期握手能维持链路」   | ❌ 每 30 秒重复发送会**打断 2.4G 链路** |

握手帧的后果：**鼠标失灵、断连重连循环**。
  
用户报告了该现象，移除后恢复正常。

### 结论

所有 `HidD_SetFeature` / `HidD_SetOutputReport` 调用已被彻底移除。
  
程序现在是**纯只读**的。

## 五、空帧识别（必须处理）

设备在**唤醒间隙**会返回整块全零的缓冲，其首字节也不是正常的 `0x01`。

若不做区分，会把空帧当成 **0% 电量**显示，产生严重误报
  
（日志中曾连续出现 4 次 `battery=0`）。

### 判别逻辑

```cpp
int bat = buf[88];
if (bat == 0) {
    bool payloadAllZero = true;
    for (size_t k = 1; k < buf.size(); ++k)
        if (buf[k]) { payloadAllZero = false; break; }

    // 只有「整块全零」才是空帧
    if (payloadAllZero) return false;
}
if (bat > 100) return false;     // 越界值同样丢弃
```

丢弃后保留上一次的有效值，不会跳变成 0%。

> **⚠ 关于首字节（2026 更正）**
>
> 早期文档写「正常帧首字节是 `0x01`」，并据此加了 `|| buf[0] != 0x01` 判据。
> **这个假设是错的**：连续 40 次读取实测首字节**恒为 `0x02`，从未出现 `0x01`**，
> 因此该条件恒为真，已删除。
>
> 但要说清它的实际影响面，别夸大：设备休眠时返回的是
> **首字节 `0x02`、其余字节全零**（并非连首字节也为零），
> 此时 `payloadAllZero` 本来就为真，该帧照样被正确丢弃。
> 所以那条多余条件**只**在「`byte[88] == 0` 且载荷其余字节非零」这一窄情形下
> 改变行为 —— 旧代码会丢弃该帧（显示「未检测到设备」），新代码显示 `0%`。
>
> 保留修复的理由是语义正确（0% 正是最该报警的时刻），而不是"修掉了一个常见 bug"。
>
> 复核方法：连续读取并打印每个字节的取值分布，看首字节是否真的出现过 `0x01`。

## 六、其他技术要点

### 6.1 输出报告需要同步句柄，输入读取需要 OVERLAPPED

- **输出报告**（本程序已不使用）要求句柄是**同步**的
- **输入读取**在空闲的无线集合上，同步 `ReadFile` 会**永久阻塞**
    
  （实测 CPU 占用为 0，程序挂死）

因此读取路径使用 `FILE_FLAG_OVERLAPPED` + 每集合独立事件 + 短超时等待。
  
本程序只用 `HidD_GetFeature`，不涉及此问题，但记录备查。

### 6.2 `HidD_GetReportDescriptor` 不是用户态导出

用户态无法调用。改用 `IOCTL_HID_GET_REPORT_DESCRIPTOR`，
  
但该 IOCTL 在本设备上始终返回 `ERROR_INVALID_FUNCTION`。

**替代方案**：用 `HidP_GetValueCaps` 遍历能力数组获取报告 ID。

### 6.3 每次读取重试一次

单次失败往往只是设备恰好处于休眠唤醒间隙。
  
重试一次可显著减少误报（重试同样只读，无副作用）。

### 6.4 驱动实际返回的长度就是请求长度（实测）

用 `DeviceIoControl(IOCTL_HID_GET_FEATURE)` 单独验证过：**请求 250 字节，
`IoStatus.Information` 就报告 250**，缓冲实际填充到 `byte[141]`（最后一个非零字节），
与 `src/RapoBattery.cpp` 里「有效数据到 141」的注释一致。

意义：任何「按驱动报告的字节数切片」的封装库（如 hidapi）在**本设备上**都不会
截断 `byte[88]`。但直接读自己申请的缓冲更稳妥。

### 6.5 能力矩阵可用纯 Python 复现

第二节的能力矩阵可由纯 ctypes 复现（直调 `setupapi.dll` + `hid.dll`），
并以 `access=0` 的**纯只读句柄**读取 Feature report。

## 八、在其它型号上的适配

手工排查的思路如下：

1. 运行 `RapoBattery.exe --read`，看能否找到集合
2. 若找不到，说明设备没有暴露 `FF00/000F` 集合 —— 需要重新枚举能力矩阵
     
   （枚举逻辑可参考 `src/RapoBattery.cpp` 的 `FindRapoCollections()`）
3. 若能找到但电量不变，说明偏移不对 —— 需要静置轮询，
     
   找出「缓慢跟随真实电量」的那个字节

### 三层判据（从强到弱）

```bat
第 1 步  看能力矩阵：哪些集合有 Feature report，UsagePage 是否 0xFF00
第 2 步  扫描各 Feature report ID，找出哪个 ID 能读到数据
第 3 步  采样并筛字节，按下面三条收敛到唯一候选
```

```
1. 结构性定位   找到 16 位小端 DPI 档位表（严格递增）→ 紧随的 01 标记
                → 其后就是电量
2. 统计筛选     候选字节需满足：值域 0..100 + 采样期内恒定 + 始终非零
3. 人工确认     让电量掉 1% 后重测，或与官方网页驱动显示值对比
```

> 只有第 3 步能定论 —— 前两步只能把候选从十几个缩到一两个。
> 本机按此流程定位到 `byte[88]`：布局为 `byte[81..86]` = 576/1000/1100 dpi
> → `byte[87]` = 01 → `byte[88]` = 电量。

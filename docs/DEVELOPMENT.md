# 开发笔记与踩坑记录

这份文档记录开发过程中**真实踩过的坑**。其中不少是典型的 Win32 陷阱，
而且有几个 bug 的根源就是「修 A 时没检查对 B 的影响」。

---

## 一、Win32 陷阱

### 1.1 `SetTimer` 投递的是 `WM_TIMER`，不是自定义消息

```cpp
SetTimer(g.hwnd, WM_POLL, 1000, nullptr);   // WM_POLL 只是个 id
```

到点后系统投递的是 **`WM_TIMER`**，定时器 id 在 **`wParam`** 里：

```cpp
case WM_TIMER:
    if (wp == WM_POLL) { ... }     // ✓ 正确
```

早期版本误写成：

```cpp
case WM_POLL:                       // ✗ 永远不会触发
    DoPoll();
```

后果：**轮询只在启动时执行过一次**，之后电量永不更新。
日志里只有一条 `first read done`，之后再无读取记录 —— 这就是根因线索。

窗口过程必须写成 `case WM_TIMER: if (wp == <id>)`。

### 1.2 `GetLastError()` 会被任何 API 调用覆盖

```cpp
SetLastError(0);
HANDLE m = CreateMutexW(nullptr, FALSE, L"...");
Dbg(L"CreateMutex: %p", m);            // ← Dbg 内部写文件/取时间/格式化
DWORD err = GetLastError();            // ✗ 已经被 Dbg 覆盖
```

后果：首次启动被误判为「已有实例在运行」，弹出对话框后立即退出。

**正确做法**：在 `CreateMutexW` 之后**立刻**读取错误码，再做任何其它调用。

```cpp
SetLastError(0);
HANDLE m = CreateMutexW(nullptr, FALSE, L"...");
DWORD err = GetLastError();            // ✓ 紧接着读
Dbg(L"CreateMutex: %p err=%lu", m, err);
```

### 1.3 `FeatureReportByteLength` 只是声明长度

见 [`PROTOCOL.md`](PROTOCOL.md) 第一节 —— 必须超额申请缓冲，否则读不到 `byte[88]`。

### 1.4 `WM_KILLFOCUS` 里销毁窗口会导致窗口「秒退」

浮窗面板曾用 `WM_KILLFOCUS` 来关闭自己，结果面板一出现就消失。

原因：点击托盘图标时，鼠标事件被路由到任务栏，面板刚创建就收到了
失去焦点的消息，于是**在用户看到它之前就自我销毁了**。

改用 `WH_MOUSE_LL` 钩子判断「点击是否落在面板之外」，
并用定时器轮询光标位置来收起子菜单。

### 1.5 `SetCapture` 会抢走全部鼠标消息

为了「点面板外部关闭」，曾经调用 `SetCapture`。后果：

**面板上的时间戳不再刷新** —— 因为 `WM_TIMER` 只有在新消息到达时才会被捎带处理，
而鼠标消息全被截给了面板。鼠标不动 → 不产生新消息 → 定时器得不到执行。

改用 `WH_MOUSE_LL` 钩子：它只**被动观察**全局点击位置，
不截获消息，因此不影响系统其它程序。

> 教训：为解决「点外部关闭」引入的机制，制造了「时间戳不刷新」的新 bug。

### 1.6 不要在窗口过程的高频消息里写文件

调试时曾在托盘回调里加了一行日志：

```cpp
case WM_TRAY:
    Dbg(L"WM_TRAY: event=0x%04X", LOWORD(lp));   // ✗ 灾难
```

**鼠标停在托盘图标上时，系统会持续向托盘窗口发送 `WM_MOUSEMOVE`（0x0200）。**
每条都触发一次同步文件 I/O（`_wfopen` + `fprintf` + `fclose`），
消息循环被彻底堵死，1 秒的定时器根本排不上队。

现象：**只有把鼠标移开托盘图标，时间戳才开始更新。**
日志里能看到连续上百行 `WM_TRAY: event=0x0200`。

### 1.8 托盘图标尺寸由系统决定，无法放大

Shell 按 DPI 请求图标尺寸：100% → 16×16，125% → 20×20，150% → 24×24。

早期实现固定渲染 32×32 再交给系统缩小到 16×16，
**白白损失一半分辨率**。现在按实际像素渲染，内部用 8 倍超采样消除锯齿。

### 1.9 `GET_X_LPARAM` 在 `WIN32_LEAN_AND_MEAN` 下不可用

它定义在 `windowsx.h` 里，而该头文件被 `WIN32_LEAN_AND_MEAN` 屏蔽。
需要自行定义：

```cpp
#define GET_X_LPARAM(lp) ((int)(short)LOWORD(lp))
#define GET_Y_LPARAM(lp) ((int)(short)HIWORD(lp))
```

## 二、浮窗面板的设计演进

面板功能迭代了多轮，每一轮的问题与修法：

| 问题 | 根因 | 修法 |
|---|---|---|
| 面板完全不出现 | 位置未做屏幕校验，`Shell_TrayWnd` 返回异常值时算出屏幕外坐标 | `MonitorFromPoint` + `GetMonitorInfoW` 钳制到工作区 |
| 面板不贴在托盘图标上方 | 用了任务栏整体矩形定位 | `Shell_NotifyIconGetRect` 取图标自身矩形 |
| 面板点一次「没反应」 | 面板其实创建在屏幕外，再点一次是「关闭」 | 同上 |
| 子菜单移开不消失 | `WM_MOUSELEAVE` 在移向子菜单的**途中**就先触发父窗口 leave | 定时器轮询光标位置 |
| 时间戳不刷新（第 1 次） | `SetCapture` 抢走全部鼠标消息 | 改 `WH_MOUSE_LL` 钩子 |
| 时间戳不刷新（第 2 次） | 托盘回调里的日志刷屏堵死消息队列 | 删除该日志 |
| 时间戳不刷新（第 3 次） | 只刷新了托盘提示，**从未让面板重绘** | 面板加定时器 `InvalidateRect` + `UpdateWindow` |
| 托盘提示与面板时间差 1 秒 | 两个独立定时器采样时刻不同，整数除法结果差 1 | 改为显示**绝对时间戳** `HH:MM:SS` |
| 提示固定 2 秒才跳一次 | 为解决「IPC 背压」加的节流，但该背压并不存在 | 删除节流 |

### 面板定时器最终设计

面板内**只保留一个** 500ms 定时器（早期是 150ms + 1000ms 两个）：

```cpp
case WM_TIMER:
    if (wp == WM_PANELTICK) {
        InvalidateRect(hwnd, nullptr, FALSE);   // 保持时间戳新鲜
        UpdateWindow(hwnd);
        PollSubClose();                          // 子菜单该收就收
    }
```

托盘悬停提示由**主窗口**的 `WM_TIP` 定时器每秒刷新。
两个定时器分工明确，不重复劳动。

> **曾经的问题**：面板定时器里也调用了 `RefreshTipOnly()`，
> 导致面板打开时提示被两个定时器叠加刷新（实际每 500ms 一次）。

## 三、图标渲染

### 3.1 为什么不用 GDI 字体

- ClearType 在 Alpha 位上会产生**黑边**
- 字体缩放会失真

改用 SVG 轮廓展平成多边形后逐像素绘制。

### 3.2 描边实现的性能陷阱

最初每个字形要按 **9 个偏移各完整重绘一遍**（`FillGlyph × 9`）来实现描边。

改成**一次轮廓求值**同时得到「是否在内部」和「到边界距离」，
内部填填充色、外侧按距离淡出写入描边色。**速度提升约 9 倍。**

### 3.3 字高不能随可用宽度浮动

早期版本「7」渲染成「92」的 1.6 倍大 —— 因为字高是从可用**宽度**推导的，
而宽度取决于位数。

修法：字高基准固定为 **2 位数**，3 位数才按宽度等比缩小。

### 3.4 数字等宽

取最宽数字的宽高比作为统一字宽，所有数字按同一宽度排版，否则参差不齐。

---

### 3.5 覆盖率公式：藏得最久的一个 bug

托盘数字一直"灰蒙蒙、对比度低"。我先后怀疑过配色、任务栏底色、描边粗细、
字形太小，每次都用对比图验证，**四次都没找对**。

真正的定位方法是**量 alpha 分布**：

```
修复前：alpha = 255 的像素 0 个，alpha 在 120..136 的 11381 个
```

所有像素都是半透明 —— 这才指向公式，而不是视觉。

```cpp
// 错：Clamp01f 会先把 (0.5f - minD) 压到 0，
//     于是任何离边界超过半个像素的内部像素覆盖率恒为 0.5
float cov = inside ? Clamp01f(0.5f - minD) + 0.5f : Clamp01f(0.5f - minD);

// 对：有符号距离覆盖率，内部离边界超过 0.5 像素即完全不透明
float cov = inside ? Clamp01f(0.5f + minD) : Clamp01f(0.5f - minD);
```

修复后 alpha = 255 的像素从 **0 个**变成 **67 个**（单个"92"图标）。

同一个错误公式在 `FillGlyph` 里还有一份，一并修掉。

**教训**：视觉问题不要靠"换参数 + 出对比图"来试。
先用数值量一次（这里是 alpha 直方图），异常值会直接指向代码。

### 3.6 预览工具会骗人

开发中写过一个 C++ 图标预览工具（为协议分析配套，未随仓库保留）。
它的 BMP 写出函数有致命缺陷：

```cpp
p[3] = 255;                                  // alpha 写死
p[0] = (b * a + bb * (255 - a)) / 255;       // 透明像素合成到固定深灰
```

所以它**无法展示浅色任务栏下的效果** —— 不管怎么贴到浅色背景上，
出来的都是一块深灰。基于它做的"浅色任务栏对比图"是错的。

改用 `tools/render_icons.py`（Python 重写同一套管线，输出真实 alpha）。
两份实现的差异只有 80/6848 像素，可以认为等价。

## 四、工程教训

### 4.1 验证要验证「值」，而不是「脚本跑完了」

修改图标描边宽度时，我三次声称「已改细」，但**实际一次都没生效** ——
替换语句跨了两行，单行匹配从未命中。

更糟的是验证脚本也误报通过：它检查字符串 `0.65f * U` 是否存在，
结果匹配到了另一行 `sOff = 0.65f * U`（虚线描边偏移）。

**教训**：改数值时，脚本必须**打印改动前后的实际原文**，而不是只检查
「某个字符串是否存在」。

### 4.2 不要用 PowerShell 的文本 cmdlet 处理 UTF-8 源码

`Get-Content` / `Set-Content` 默认按系统代码页（简体中文系统为 GBK）解码，
往返一次会把源文件里**所有非 ASCII 字符变成乱码**，
并且会把 `\n`、`\"` 这类转义序列还原成实际字符，**撕坏字符串字面量**。

本次开发中这个操作毁掉了整个文件的 99 行中文注释，修复花了数轮。

**正确做法**：用 Python 显式指定编码读写。

```python
import io
s = io.open(path, encoding="utf-8").read()
io.open(path, "w", encoding="utf-8").write(s)
```

### 4.3 交付前先删除调试代码

调试用的计数器（`tickPanel` / `tickTip` / `paintCount`）、
`Dbg(L"POLL battery=%d")` 之类的跟踪语句，如果留在生产代码里，
轻则污染日志，重则像 §1.6 那样**变成新的性能 bug**。

### 4.4 先拿运行时证据，再改代码

浮窗排查过程中，「读代码推断」连续猜错多次
（`WM_KILLFOCUS`、`SetCapture`、IPC 背压、日志刷屏），
而每次真正的证据都来自日志。

**建议**：GUI 问题（位置、Z 序、消息抢占、激活状态）光看代码很难区分，
应该**先加日志拿到运行时真值**。
